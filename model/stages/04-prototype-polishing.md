# 原型精修

## 进入、职责与输出

- 触发：功能符合要求后需要更合适的视觉与交互设计；默认位于原型审查之后，设计探索可提前，最终改动仍需重新审查与回归。
- 输入：当前A05 UI与交互规格、A03行为与权限规则、A12与A25审查及解读结论、设计与可访问性约束、既有设计资产与许可。
- 产出：[制品目录](../artifact-catalog.md)中的 A27视觉与交互设计交付包、更新的A05、按确认设计调整的A11实现，以及行为变化时的A03/A10更新与A16待重验项。
- 人与AI分工：人决定设计方向、来源与确认交付；AI按实际工具能力组织设计提示词或准备设计简报、解释差异、比较方案、检查交付完整性并实施改动。
- 退出：确认的设计交付包齐备（含状态、响应式、可访问性、素材来源与许可），实现与之一致，行为变化已同步规格与验收项并回归，重新审查范围明确。
- 失败/返回：未确认图稿不得自动视为新业务要求；行为变化回[原型构建](01-prototype-building.md)澄清，整体目标变化回A01范围决策；表现问题在本活动内处理。

设计支持三种来源：专门的设计AI、人工设计或外包、两者混合。混合来源须记录各部分来源、版本、修改关系与使用限制，不把人工设计伪写成AI生成。精修可引起局部功能调整，但整体目标不变；影响按权限、数据、业务流程及验收标准评估，不按修改行数判断。

## 执行步骤与提示词

下面每一条都可直接给AI执行。参数从本活动输入和[提示词协议](../practices/prompt-protocol.md)取得；缺少参数先读取可发现事实，再澄清。已有授权足够时连续执行，不逐条重新索取批准。文件操作需要读写权限，运行/验证另需终端和对应环境；UI需要浏览器与设计工具能力。

### POLISH-START：明确精修目标与约束

```text
[POLISH-START] 请为 {目标} 建立精修上下文：读取 {输入路径}（A05 当前规格、A03 行为与权限、A12/A25 结论、设计与可访问性约束），列出待改善的界面与交互、必须保持的行为、适用视口与状态清单及所需能力（浏览器、设计工具）。区分表现问题与行为问题，不扩大功能范围。
```

预期输出与判断：精修范围、约束与状态清单。若条件不满足，使用 POLISH-DECIDE 或 POLISH-RECOVER。

### POLISH-DECIDE：选择设计来源与取舍

```text
[POLISH-DECIDE] 针对 {设计问题}，请比较三种来源的可行方式：专门的设计 AI（文生图与图生图，按实际工具能力和表达习惯组织提示词，不固定一家产品的专有语法）、人工或外包（设计简报、交付清单与反馈记录）、混合（记录各部分来源、版本与使用限制）。给出成本、可控性、许可与迭代速度差异及推荐项；设计方向由人决定，不把人工设计伪写成 AI 生成。
```

预期输出与判断：来源比较、推荐与待决方向。若条件不满足，使用 POLISH-RECOVER 或上文指定的返回路径。

### POLISH-GENERATE：产出设计交付并实施

```text
[POLISH-GENERATE] 请依据 {确认来源} 生成 A27：设计简报、来源与工具、参考与效果图、源文件、交互说明、加载/空/错误/权限状态、响应式、可访问性、素材来源与许可、行为差异及确认记录；据此更新 A05 并调整 A11 页面与相关实现。静态效果图无法表达的交互必须补充文字说明；未确认图稿只作候选，不当作新业务要求实施。
```

预期输出与判断：完整设计交付包与对应实现改动。若条件不满足，使用 POLISH-RECOVER 或 POLISH-DECIDE。

### POLISH-REVIEW：检查交付完整性与影响分类

```text
[POLISH-REVIEW] 请审阅 {设计交付或实现差异}：交付项是否齐全（状态、响应式、可访问性、素材来源与许可、版本与修改关系），实现是仅改表现还是改变行为；按权限、数据、业务流程与验收标准评估影响，不按修改行数判断。列出需更新的 A03/A05/A07/A16 项与需人决定的取舍；发现具体问题模式时按 A26 做全项目同类排查。
```

预期输出与判断：交付缺项、影响分类与待决取舍。若条件不满足，使用 POLISH-GENERATE 补齐交付。

### POLISH-VERIFY：验证视觉交互与回归

```text
[POLISH-VERIFY] 请对 {候选} 按 A05 与 A07 验证：在约定视口与缩放条件下检查布局、焦点与语义、加载/空/错误/权限状态；行为变化处重跑受影响 A03 用例与回归。记录实际观察手段与证据（截图证明外观，接口与数据结果证明权限与持久化）；未执行的项记无法判定。
```

预期输出与判断：视觉交互与行为回归的真实结论。若条件不满足，使用 POLISH-RECOVER。

### POLISH-HANDOFF：移交确认设计与实施结果

```text
[POLISH-HANDOFF] 请把精修结果交给下一执行者，保存到 {交接路径}：确认的设计交付版本、更新的 A05 与实现范围、表现与行为变化分类、受影响验收项与待重验证据、需重新审查的范围及下一步。
```

预期输出与判断：可恢复的交接与重新审查范围。若条件不满足，先补足版本、分类或未决项。

### POLISH-RECOVER：交付缺项或误当作需求

```text
[POLISH-RECOVER] 处理 {失败或冲突}：设计交付缺项、素材许可不明、未确认图稿被实施、视觉改动引入行为回归。回退到最近确认版本，列出缺项与解除条件，区分表现问题与业务语义变化；缺少会改变业务语义的决定时暂停相关修改，其余已确定工作继续。
```

预期输出与判断：回退结果、缺项与解除条件。若条件不满足，记录阻塞并保留已确认版本。

## FocusTask 教学填写示例

示例输入为 [FocusTask 教学上下文](../../examples/focustask/docs/context.md)。以下指令生成精修类文档，运行与视觉检查未执行，不作通过结论。

```text
[POLISH-START / 已填参数示例] 从仓库根读取 examples/focustask/docs/context.md
及对应的 A01–A28 规范、模板与教学例。请填写 A27 与 A05 教学例：以任务列表与创建表单为对象，
列出 1440x900、1024x768、768x1024、390x844 视口与 200% 缩放下的状态清单、焦点与可访问性要求、
素材来源与许可，以及仅表现变化与行为变化的分类。不生成真实图稿、不联系设计师；视觉与运行检查标注未执行。
若实际项目要执行本活动，请先提供当前 UI 规格、设计约束、确认来源与授权。
```

## 交接出口

只有上文退出条件满足才进入[原型审查](03-prototype-review.md)重新审查受影响实现，再进入[独立验收](05-verification.md)。仅表现变化时更新设计与视觉检查即可，但仍在A16标记待重验项；行为变化必须同步A03、A10与受影响验收项。需要返工时在A15注明原因、影响、返回活动和重验范围；模板、候选自检和教学示例不能代替独立证据。裁剪与并行安排记录在A10，见[裁剪](../tailoring.md)；裁剪不取消适用的确认、测试、审查与证据要求。
