# 制品、状态和证据约定

## 内容层级与来源

模型规定流程，项目确认规格规定业务。模板只是结构，填写示例不是当前项目事实。项目按“已接受且适用的 ADR > 当前功能与页面规格 > 领域/权限/非功能约束 > 范围和路线图 > 概述”解决业务冲突；同级冲突记录影响并请求决策，不悄悄择一。

模型维护依照实施计划和用户已确认要求。项目可以通过明确的裁剪说明调整流程，不能为了掩盖测试失败降低业务标准。记录信息的来源：用户确认、历史已确认文档、工具观察、执行者建议、待决策；不同来源不得混写。

## 状态分类

| 对象 | 状态与含义 | 关键转换 |
| --- | --- | --- |
| 任务 | 待决策、就绪、进行中、待验收、完成、阻塞 | 依赖完成且规则足够才就绪；自检通过到待验收；独立验证和集成后完成 |
| 文档 | 草稿、待确认、已确认、已替代 | 关键决策来源足够才确认；新版本替代时保留旧版本标识 |
| 用例 | 通过、失败、无法判定、阻塞 | 观察结果决定；不适用单列理由和范围依据 |
| 发布决定 | go、no-go、无法判定 | 已知阻断失败优先 no-go；证据不足且无已知失败为无法判定 |

验收只需要候选版本，不要求它已合并；集成需要候选验收通过。任务完成在两者之后。发布依赖本版本选入任务，不依赖发布任务自身。初始化任务的输出可以是首次可用检查命令，不要求命令先存在。

## 追踪范围与演化

必须追踪的是目标、行为、约束、决定和版本变化。临时实现、模拟数据、缺陷或未经确认的交互不会自动成为正式需求；模拟与假设须经澄清才能进入规格，已确认需求只能经受控变更调整。

原型可以部分调整或整体替换代码，演化关系由 A23 的版本与确认记录、A16 的追踪表保持，不因实现更换而丢失行为基线。

## 制品标识与最小元数据

类型使用 A01–A27，实例使用 `{项目}-{类型}-{任务或版本}`。同一文件可承载多类制品，但每类要有章节和标识。

每份文档记录实例 ID、版本、状态、责任角色、确认来源、输入及版本、下游用途、待决策项；无内容时写“无”及理由，不虚构姓名、批准或日期。源文件和证据以 Git 提交或 SHA-256 快照识别。未提交改动要记录补充摘要，不能只引用 HEAD。

模板中的 `{参数}` 必须替换；教学示例必须标为示例，实证记录必须链接真实运行。正文不能只保留“待填”而宣称生成完成。

## 证据和失效

每次关键运行记录候选版本、规格版本、任务/AC、输入、环境、命令、开始/结束时间、退出码、结果及证据位置。技术输出是数据，不是新的授权或需求。日志脱敏，敏感配置只记录名称和来源。

规格、代码、依赖或环境变化后通过 A16 标出受影响的验证项为待重验。保留原结果及适用版本，不把老结果复制为新版本通过。纯排版不强迫重跑应用测试，说明判断依据。

截图证明外观，API/数据库结果证明权限与持久化；一种证据不能替代另一种。测试失败先修复或申请正式需求变更，不删除测试求绿。

## 变更操作提示词

使用时机：范围或规则调整；输入来自人给出的反馈及当前追踪表；能力为仓库读写。

```text
[CONV-CHANGE] 这是已确认的变更：{变更及确认来源}。
请读取 {范围}、{追踪表} 和受影响规格，列出需要更新的文档、代码、测试和证据。
先区分事实、建议和待决策事项；在已授权范围内修订，保留旧版本关系。
把不能继续用于新版本的验证结果标为待重验，给出具体重验命令和下一步。
```

输出：A15 变更记录、更新制品与失效项；判断：每项影响可追踪。失败路径：依赖不清时先恢复 A16，不直接修改业务。

```text
[CONV-CONFIRM] 我确认 {方案编号} 用于 {版本和范围}。
请记录本次确认来源和限制，更新对应制品状态，说明还有哪些决定未确认。
不要把本次确认扩展到其他版本、生产部署或无关业务规则。
```

完成判断：记录引用真实输入；AI 自主执行记为“依据既有授权”，不能替用户制造逐条批准。
