# 验证、评审与完成

## 先确定判据

A07在实现前定义风险与验证策略；A14针对固定候选独立执行，A12记录评审，A16连接全部结果。文档改动检查语义、链接与一致性；应用行为变化运行真实自动化测试，不为可逆排版改动强造测试。

完成至少包含：范围正确、规则可追踪、自检实际通过、适用AC有独立证据、差异经评审并集成、交接可恢复。没有托管PR时采用本地评审和版本化候选，不虚构平台状态。发布质量由A17–A19另外验证，不把发布检查强加给每次文档修订。

首轮实证改进：共享生成目录的检查保持顺序。例如Next构建会重建.next，不能与读取.next/types的类型检查同时运行。出现这种竞争保留失败日志，再在构建结束后重验。记录每种验证方法的真实边界：等效视口不等于真实浏览器缩放，浏览器引擎不等于移动实机。

真实缩放还要检查活动控件边界与覆盖：一次按钮点击成功不能证明所有字段可用，fullPage长截图可能掩盖固定操作区的覆盖。必要时补当前视口截图、元素几何数据及滚动后的填写动作；发现范围内缺陷应重新打开交付验收并生成新候选，而不是把它写成证据局限后直接通过。

## 证据要求

| 结论 | 必须具备 |
| --- | --- |
| 通过 | 标准与候选版本、真实步骤和符合预期的结果 |
| 失败 | 预期、实际、复现、环境、证据和影响 |
| 无法判定 | 具体缺少的规则/证据及需要补充什么 |
| 阻塞 | 外部条件、错误、已尝试方案与解除条件 |

UI截图、接口响应、数据库数量分别支持各自结论。用例名相符或测试数量多不能证明覆盖；需读取断言是否针对要求。质量工具配置为空或脚本固定exit0不能称为通过。

## 操作链

输入：规格、候选、环境与可运行命令；独立验证需要不受编码者自评影响的上下文。

```text
[QA-PLAN] 请依据 {范围和AC} 建立A07，列风险、测试层次、夹具、环境、命令和证据。
说明每条规则由哪个断言判定；缺工具列阻塞，标准不明先澄清。
标出会读写同一生成目录或共享数据的命令，顺序执行这些命令；并行仅限彼此独立的检查。
```

```text
[QA-RUN] 请只读验收 {候选}。先核对源码/规格摘要，再运行 {检查入口} 与AC。
逐项记录实际结果；UI覆盖规格的视口和状态，权限还需API与数据证据。
在缩放/小屏中检查活动字段和固定操作区是否重叠，补视口截图和边界数据，不能只以按钮可点判断全部UI通过。
把失败写入A15；不要修改实现或放宽标准让它通过。
```

```text
[QA-EXPLAIN] 请解释 {验收报告}：哪些证据支持结果、哪些范围尚未验证、什么阻止集成或发布。
对失败给出返回需求/设计/实现的建议。我的 {反馈} 若改变需求，先记录变更再重验，
否则只修复实现；不要删除原失败证据。
```

```text
[QA-RECHECK] 对 {修复候选} 执行原失败用例与影响回归，更新A14/A16。
确认测试确实检查原问题；记录旧失败、新结果与版本。通过后交给集成/发布，
没有运行结果时保持未验证。
```

填写示例：AC-08相同幂等键重试需同任务ID且仅一条数据；AC-09 Viewer需403且无写入；浏览器按钮隐藏不能替代这两个断言。
