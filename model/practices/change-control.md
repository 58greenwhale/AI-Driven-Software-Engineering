# 变更、缺陷和返工控制

## 入口与边界

先建立A15再改代码。需求变化是新目标；缺陷是未满足已有标准；人为故障必须标演练。AI分析影响、提出方案，人对新业务语义负责；已确认修复范围可以连续执行。

A16追踪受影响制品，保留旧版本证据并将新版本相关项标待重验。不可逆数据变化单独确认，禁止修改旧迁移掩盖历史。

同类问题排查是横贯规则：从已发现的问题提炼根因与模式，用文本、结构和业务语义在全项目搜索同类实例及变体，区分已确认、疑似和不适用，修复确认项后回归并再次排查，结果写入A26并关联A12/A15/A16。此规则适用于四项开发活动、独立验收发现的缺陷和维护；疑似项先验证再改，不按相似度直接替换。未发现其他实例也要记录搜索范围、方法、结果与限制，不能检查的模块明确记录，未检查部分不写成没有问题。操作链见[原型审查](../stages/03-prototype-review.md)，记录要求见[A26规范](../artifacts/A26-pattern-remediation.md)。

## 提示词

```text
[CHANGE-START] 请把 {问题或新要求} 写成A15，区分真实缺陷、需求变化与演练。
读取 {运行版本与规格}，给出现状/期望、复现、影响与返回阶段。先分析，不直接改代码。
```

输入来自反馈与真实运行；输出为可判定的问题，不接受“优化一下”作为完整范围。

```text
[CHANGE-DECIDE] 针对 {问题编号} 比较最小修复与其他可行方案，说明规格、数据、兼容和测试影响。
按 {真实选择或既有授权来源} 记录决定。新增业务权限没有依据时暂停相关部分，
不因实现方便改变规则。
```

```text
[CHANGE-EXECUTE] 按已确认A15更新受影响规格、契约、代码和测试，保持任务范围。
列哪些旧证据失效，执行原失败用例和相关回归。需要再发布时使用REL流程，
不要把自检当已部署或把故障副本混入正常产物。
```

```text
[CHANGE-CLOSE] 核对 {问题编号} 的原始现象、新候选、回归、再发布与数据结果。
有证据才关闭；否则明确阻塞。写A20并把交接/追踪/模型评价同步，
说明哪些提示词或文档缺口导致返工以及重验方式。
```

教学示例：CHANGE-teaching-filter 增加状态筛选，保持创建默认 todo；假设的权限缺陷为 Viewer 可写，不能修改 Viewer 只读规则。实际项目修复失败时保留证据，再按根因返回受影响开发活动；本示例不启动应用或演练。
