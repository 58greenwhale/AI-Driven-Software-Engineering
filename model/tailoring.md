# 裁剪、组合与并行

## 不可裁剪的能力

目标和关键规则有责任人；AI 读取确认规格；改动有版本；验证有真实证据；变更能追踪；失败不冒充通过。可以把多个制品放在一个文件，不能省略下游需要的信息。

| 方面 | 个人 | 小团队 | 大型团队 |
| --- | --- | --- | --- |
| 人的角色 | 一人兼产品/技术责任，明确哪些决定自己负责 | 指定范围、技术、发布责任角色，可兼任 | 责任映射到团队与接口所有者，明确跨团队决定 |
| 文档 | A01–A07 可合并为规格包，保留编号章节 | 按功能/契约拆分，共享领域规则 | 按服务边界拆分，契约有版本和兼容窗口 |
| 任务 | 一个短任务分支或可追踪本地候选 | 任务分支与评审 | 跨团队依赖计划和集成候选 |
| 评审 | 独立检查会话及本地记录，无托管 PR 时如实说明 | 同伴或独立 Agent 评审，明确责任人 | 风险触发专业审查，授权门禁受团队政策约束 |
| 发布 | 隔离目标与恢复手段 | 共享测试环境和发布责任人 | 分批发布与审计；具体生产策略由项目制定 |
| 证据 | 小型文件和脚本入口 | 共享证据索引 | 访问受控的制品库，设置保留与追溯 |

## 活动组织与并行

| 组织方式 | 执行方式 | 必须解释的组织条件 |
| --- | --- | --- |
| 按功能 | 每项功能依次执行适用活动，不同功能可并行 | 功能边界、共享接口、依赖、工作区或文件归属、集成顺序 |
| 按迭代 | 本轮功能整体构建，再整体重构、审查、精修 | 本轮范围、统一约束、候选版本、整体交接及验收 |
| 混合组织 | 先统一公共约束，各功能分别推进，最后集成 | 公共制品责任、变更传播、冲突处理、集成后的重验范围 |

A10 记录执行粒度、采用的活动、合并/简化/跳过理由、依赖、并行边界、共享制品和集成条件。不同功能可处于不同活动，一项功能的就绪状态不代表全部功能。

无 UI 项目可省略视觉精修；已满足工程约束的原型可简化重构；小改动可合并活动。裁剪活动形式不取消适用的确认、测试、审查及证据要求。

并行时共享的功能规格、领域权限、接口、架构和设计规则要有明确维护入口；冲突必须解决并更新受影响功能，集成后验证跨功能路径。执行可以由一个 Agent 完成，也可以按已授权分工使用多个 Agent，分工与集成规则见[上下文与交接](practices/context.md)。

项目负责人根据功能、团队、风险和技术约束人工选择组织方式，决定哪些活动适用、合并、简化或跳过。将选择及其理由、依赖、并行边界、共享制品责任、集成顺序和集成后重验范围记录在 A10；裁剪不需要额外的 AI 审批流程。

## 条件制品

无 UI 不生成 A05，但保留接口验收；无持久化可将迁移标为不适用；无重要取舍不强制新增 ADR；未跨会话可把交接并入交付报告；无在线服务仍应记录构建交付和撤回方式。A21/A22 在研究实证必需，在普通产品项目可简化为决策与改进记录。

A23–A27 同样可裁剪但不省略下游需要的信息：无 UI 不生成 A27，仍保留 A05 的交互与状态验收；无重构需要不强制 A24；轻量项目可把 A23 并入 A10 或 A16 章节，但保留版本、运行入口、模拟边界与确认来源；A25 首轮系统审查后必要，可按模块增量；A26 在发现问题时必要，未发现其他实例也要记录排查范围、方法与限制。
