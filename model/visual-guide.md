# 生命周期模型图解

这三张图分别说明阶段如何推进、人如何驱动 AI、制品如何支撑下游工作。它们表达的是[模型总纲](overview.md)和[制品规范](artifact-catalog.md)，不是某个版本已经验收通过的证明。

## 1. 生命周期总览：六阶段与反馈

![生命周期总览：人驱动 AI 推进需求、设计、实现、验证、发布与维护，问题返回受影响阶段](diagrams/lifecycle.svg)

[查看高清 PNG](diagrams/lifecycle.png) · [下载 SVG](diagrams/lifecycle.svg) · [编辑 Mermaid 源码](diagrams/lifecycle.mmd)

从上往下读：人通过目标、约束、提示词和反馈驱动全流程；中间是每轮迭代的六个阶段；底部是持续支撑它们的机制。阶段间实线箭头表示正常推进，虚线箭头表示问题反馈与返工，底部无箭头连线表示共同支撑。

- **不是一次走完的单向流程**：验证发现规则缺失、契约矛盾或实现缺陷，分别返回需求、设计或实现；维护的新要求、修复与部署问题也回到相应阶段。
- **初始化不在每轮重做**：首次或重大环境变化时建立 Agent 工作规则与可执行基线，后续只补齐受影响内容。
- **每个出口都有依据**：实现产出可验收候选，独立验证后才进入发布；发布后的健康、数据和业务冒烟形成另一组证据。
- **人不逐步代替 AI 执行**：六个阶段都由 AI 完成具体工作；人负责意图与重要取舍，AI 同时辅助分析与审阅。

阶段指南：[需求分析](stages/requirements.md)、[设计](stages/design.md)、[实现](stages/implementation.md)、[验证](stages/verification.md)、[发布](stages/release.md)、[维护](stages/maintenance.md)。

## 2. 协作时序：一个阶段内部如何工作

![人、执行AI、仓库工具环境与独立验证AI之间的交互顺序](diagrams/collaboration.svg)

[查看高清 PNG](diagrams/collaboration.png) · [下载 SVG](diagrams/collaboration.svg) · [编辑 Mermaid 源码](diagrams/collaboration.mmd)

横向四列是职责，纵向是时间。人的启动、选择、修订、验证和交接操作都有[示例提示词](practices/prompt-protocol.md)。AI 先查已有事实，再对无法查明的关键问题提出选项；已有授权充分时可连续执行这些步骤。

“独立验证 AI”表示独立的验证职责、确认标准和判断上下文，不要求一定购买另一种模型或使用多人团队。验证者可以读代码、运行测试和准备隔离测试数据，但不修改产品实现来让验收通过。发现问题后保留旧结果，更新受影响制品，并用同一判据验证新候选。

时序图中的人参与表示驱动关系，不意味着每条消息都要重新批准；实际可以使用已确认的范围和授权批次。缺证据或外部条件阻塞时不能越过出口；交接记录既可以交给下一阶段，也可以用于恢复当前未完成工作。

操作样板：[A03 功能规格](artifacts/A03-feature-spec.md) · [A13 会话交接](artifacts/A13-handoff.md) · [A14 独立验收](artifacts/A14-acceptance.md)。

## 3. 制品流转：输出如何成为下一步的输入

![A01至A22制品在首次准备、六阶段和跨阶段机制中的位置](diagrams/artifacts.svg)

[查看高清 PNG](diagrams/artifacts.png) · [下载 SVG](diagrams/artifacts.svg) · [编辑 Mermaid 源码](diagrams/artifacts.mmd)

图中每个 A 编号对应一种制品类型，全部内容规范、模板、示例与生成提示词可从[制品目录](artifact-catalog.md)进入。位置表示主要使用关系，并非只能在该阶段创建；例如 A10 任务计划在实现前准备并持续更新，A12 评审不限于代码。

| 表达层次 | 读图要点 |
| --- | --- |
| 首次准备 | A08 约定 Agent 如何工作；A09 提供真正可执行的工程环境。 |
| 阶段产出 | A01–A07 定义目标、规则、设计和判据；A10–A12 形成实现与评审；A14 支持验收；A17–A20 支持发布和维护。 |
| 跨阶段制品 | A06 记录重要决定，A13 支持接手，A15 管理缺陷和变更，A16 连接需求与证据，A21 保留真实人机交互，A22 评价模型并指导修订。 |

同一制品可以增量修订，多种制品可以共用文件；有条件的制品按项目触发，而不是每轮机械地产生 22 份文档。A05 只在有 UI 时需要，ADR 由重要取舍触发，A22 在实证前先定评价问题、实证后填结果。证据必须绑定规格和候选版本，变更后只重验受影响部分。

对于文档制品，统一提供**内容规范、生成与确认提示词操作链、空白模板、填写后的示例**。A09 工程基线、A11 实现包、A17 关联构建等还包含代码或配置等非文档产物，不能用一份说明代替实际实现和运行结果。

## 如何维护与导出

图的唯一可编辑源为 `model/diagrams/*.mmd`；SVG 和 PNG 由同一份源码生成。图更新时同步核对[状态与证据约定](conventions.md)，不要把图中的概括当成新的业务规则。

见[渲染说明](diagrams/README.md)。初次使用建议先看总览，再看协作时序；执行具体任务时回到对应阶段与制品操作指南。团队裁剪方式见[裁剪规则](tailoring.md)。
