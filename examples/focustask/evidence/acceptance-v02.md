## APP-06：创建中后退的旧回调覆盖

判据来源：TASK-004 的 URL 为可恢复选择来源、慢响应不覆盖后来选择，以及 CF-04/CF-07。

预期：用户在 done 筛选提交创建，响应待返回时后退到 todo，返回后 URL、选择器、结果和成功提示均按当前 todo 状态显示，新任务可见。

原实现：[tasks.tsx](../app/src/features/tasks.tsx) 原第166–171行的提交回调捕获提交时 `status` 和 `load`；请求返回后使用旧 `status` 发提示并调用旧 `load()`。原第55–56行每次调用 `load` 都递增代次，因此这个较晚启动的旧筛选请求会成为最新代次，现有 generation 检查不能阻止它覆盖当前 todo 列表。旧角色/归档错误分支也调用捕获的旧 load。

复现步骤（初次审查为代码控制流推导，未声称当时运行浏览器）：先选 todo，再选 done；打开表单提交；拦截 POST，先让服务端完成创建但延迟向页面交付响应；浏览器后退到 todo；释放 POST 响应。原回调会请求 done 并显示“不符合当前筛选条件”，虽然 URL/选择器是 todo。现有原 CF-07 仅延迟 GET，不包含这个 POST 与历史导航组合。

初次结论：失败。该缺陷影响新筛选的明确行为，阻止原固定产物发布。

协调者修补后，`load(filter = status)`接受显式筛选值；POST成功/权限错误回调从当前浏览器 URL 获取 status，再生成提示与重新加载。独立只读探针从现有 TSX 提取并转译实际 load/submit 函数，以替身 API 模拟旧 done 提交、当前 todo 已加载、再交付旧 POST：结果仍为 todo、提示“任务已创建”，后续 GET 带 status=todo。该探针未运行 React/浏览器，不替代新增三引擎回归。

## 真实 HTTP 慢依赖补充及剩余限制

[http-fault原始日志](runs/2026-09-19T03-06-30-606Z-http-fault.log)及[结果](http-fault.json)记录真实Next生产HTTP进程连接受控回环TCP端点；该端点接受连接但不响应数据库协议。health和auth/login分别在5017.508ms、5007.386ms返回503 UNAVAILABLE、通用消息和请求ID，均小于10秒。已读取[执行脚本](../app/scripts/http-fault.mjs)，它使用临时端口、虚构连接配置及任务自建子进程，不停止正常数据库。

结论：通过此真实HTTP及停滞数据库握手场景。该运行早于rc2，但与rc2的产品差异仅客户端tasks.tsx；服务端api/db/auth及依赖一致，因此服务端故障处理结论适用。不能把它写成rc2包重新执行过全套故障测试，也不能从连接超时推断CPU阻塞时限、已经建立连接后的所有数据库慢查询、底层事务取消或所有后续副作用均受保证；这些仍无法判定。
