# 端到端用户旅程

> 迁移说明：保留的 FocusTask 产品规格输入；本地实证仅覆盖选定切片，范围与状态以 [实证范围](empirical-scope.md) 和 [实证任务表](iteration-plan.md) 为准。本文不是功能已实现的证明。

## Journey 01：新团队建立第一个项目

### 目标

项目负责人从登录开始，完成项目创建、成员邀请和第一条任务创建。

### 前置条件

- 用户 A 和用户 B 都已有账户；
- 用户 A 尚未创建任何项目；
- 用户 B 不属于用户 A 的任何项目。

### 流程

1. 用户 A 登录。
2. 系统显示项目空状态和“创建项目”入口。
3. 用户 A 创建项目“网站改版”。
4. 系统将用户 A 添加为项目 Admin，并进入项目页。
5. 用户 A 使用用户 B 的邮箱邀请其加入，角色为 Editor。
6. 用户 B 登录并接受邀请。
7. 用户 A 创建任务“确认首页文案”，负责人选择用户 B，截止日期设为未来日期。
8. 用户 B 刷新任务列表，看到该任务。

### 成功条件

- 项目只有一条记录；
- 用户 A 是 Admin，用户 B 是 Editor；
- 任务属于“网站改版”，状态为 `todo`，负责人为用户 B；
- 用户 B 无法管理项目成员或归档项目。

### 失败恢复

- 邀请失败时项目仍然存在，用户可重试邀请；
- 创建任务失败时保留表单输入，不产生部分任务；
- 重复点击创建任务只产生一条任务。

## Journey 02：成员完成任务

### 前置条件

- 项目“网站改版”处于 active；
- 用户 B 是 Editor；
- 用户 B 负责一条 `todo` 任务。

### 流程

1. 用户 B 登录并进入项目。
2. 用户 B 按“分配给我”和“未完成”筛选任务。
3. 用户 B 打开目标任务。
4. 用户 B 将状态改为“进行中”。
5. 完成工作后，用户 B 将状态改为“已完成”。
6. 用户 A 打开项目列表并看到更新后的状态。

### 成功条件

- 状态转换符合 `domain.md`；
- `updatedAt` 和 `version` 正确更新；
- 用户 A 无需重新登录即可通过刷新看到最新状态；
- 浏览器返回列表时保留原有筛选条件。

### 并发场景

如果用户 A 在用户 B 提交之前修改了同一任务，用户 B 的旧版本更新必须被拒绝，页面提示重新加载，不能静默覆盖用户 A 的修改。

## Journey 03：只读成员访问项目

### 前置条件

- 用户 C 是项目 Viewer；
- 项目包含至少一条任务。

### 流程和预期

1. 用户 C 进入项目并查看任务列表。
2. 页面不显示新建、编辑或改变状态的入口。
3. 用户 C 可以打开任务详情查看内容。
4. 用户 C 直接调用创建任务 API，服务端返回 `403`。
5. 数据库中的任务数量保持不变。

## Journey 04：归档项目

### 前置条件

- 用户 A 是 Admin；
- 项目处于 active。

### 流程和预期

1. 用户 A 在项目设置中选择归档并确认。
2. 项目状态变为 archived，并记录 `archivedAt`。
3. 所有成员仍能查看项目和任务。
4. 页面显示归档和只读提示，隐藏全部写操作。
5. 任何角色直接调用写 API 都被拒绝，数据不发生变化。
