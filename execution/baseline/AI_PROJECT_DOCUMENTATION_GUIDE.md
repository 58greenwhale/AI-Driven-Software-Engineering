# AI 项目需求与验收文档指南

## 1. 文档目的

这套文档用于让编码 Agent 和验收 Agent 对项目形成一致理解：

- 编码 Agent 知道需要实现什么、有哪些约束，以及哪些事项不能自行决定。
- 验收 Agent 能根据明确的步骤和预期结果，独立判断功能是否通过。
- 产品、设计和开发过程中的关键规则有唯一的信息来源，减少口头约定和隐含假设。

这里所说的 SOP，不只是传统的操作流程，而是可供 AI 执行和验收的功能规格。每项要求都应尽量做到可观察、可复现、可判断。

## 2. 基本写作原则

### 2.1 描述结果，不只描述意图

避免：

> 页面应当简洁、高级、易用。

推荐：

> 页面采用现有设计系统；主要操作在首屏可见；在 390px 和 1440px 宽度下不得出现元素重叠、文字溢出或非预期横向滚动。

### 2.2 一条要求必须能够判定通过或失败

避免：

> 保存速度要快。

推荐：

> 在正常网络环境下，用户点击保存后 2 秒内显示成功状态；保存期间按钮不可重复提交。

如果暂时无法确定标准，应明确标记为“待决策”，不要让 Agent 猜测关键业务规则。

### 2.3 同时覆盖正常、异常和边界情况

每项功能至少考虑：

- 正常流程；
- 空数据和初始状态；
- 非法输入；
- 加载与请求失败；
- 权限不足；
- 重复点击或重复请求；
- 网络中断和重试；
- 并发修改；
- 数据量较大时的表现。

### 2.4 区分必须实现、建议实现和不在范围内

使用明确的优先级：

- `P0`：本次必须实现，否则不可交付；
- `P1`：重要，但不阻塞核心流程；
- `P2`：后续优化；
- `Out of scope`：明确不在本次范围内。

## 3. 单个功能规格模板

每个功能建议使用一份独立文档。

```markdown
# 功能：创建任务

## 元信息

- 编号：TASK-001
- 优先级：P0
- 状态：待开发
- 依赖：用户登录、项目权限

## 目标

登录用户可以在拥有编辑权限的项目中创建任务。

## 范围

- 包含：单个任务创建、表单校验、创建结果反馈。
- 不包含：批量创建、任务模板、任务提醒。

## 角色与权限

- 项目编辑者可以创建任务。
- 只读成员不能创建任务。
- 未登录用户不能访问创建接口。

## 前置条件

- 用户已登录。
- 项目存在且未归档。
- 用户拥有该项目的编辑权限。

## 输入与业务规则

- 标题：必填，去除首尾空格后长度为 1–100 字。
- 截止日期：可选，不得早于今天。
- 负责人：可选，必须是当前项目成员。
- 创建请求必须防止重复提交。

## 正常流程

1. 用户进入项目任务列表。
2. 用户点击“新建任务”。
3. 系统显示创建表单。
4. 用户填写合法内容并提交。
5. 系统创建任务并关闭表单。
6. 新任务出现在当前项目的任务列表中。

## 异常与边界

- 标题为空或超长：阻止提交，显示对应字段错误，不创建任务。
- 负责人不是项目成员：拒绝提交，并提示用户重新选择。
- 网络失败：保留已填内容，显示重试入口。
- 权限不足：拒绝创建并显示无权限提示。
- 连续点击提交：最多创建一条任务。
- 会话过期：引导用户重新登录，不丢失可恢复的表单内容。

## 数据变化

- 新增一条任务记录。
- 任务默认状态为“待处理”。
- 记录创建人、创建时间和所属项目。
- 创建失败时不得产生不完整记录。

## 验收用例

### AC-01：成功创建

给定用户拥有项目编辑权限，且输入合法标题，
当用户提交表单，
那么列表中出现且只出现一条新任务，刷新页面后任务仍然存在。

### AC-02：标题为空

给定标题只包含空格，
当用户提交表单，
那么页面显示“请输入任务标题”，并且任务数量不变。

### AC-03：重复提交

给定用户连续点击两次提交按钮，
当请求处理完成，
那么系统中只创建一条任务。

## 完成证据

- 相关自动化测试通过；
- 正常、失败和空状态的页面截图；
- API 或数据库结果能够证明数据变化正确；
- 已记录未解决的问题和已知限制。
```

## 4. UI 页面规格模板

不要只使用“现代、简洁、高级”等主观词语。UI 文档需要描述布局、内容、状态、交互、响应式行为和视觉验收方式。

```markdown
# 页面：项目任务列表

## 页面用途

让项目成员查看、筛选、创建和进入任务详情。

## 设计依据

- 设计稿或参考图：[链接或文件路径]
- 必须遵循：布局、信息层级和交互方式。
- 以现有项目为准：颜色、字体、间距、图标和基础组件。
- 禁止事项：不得新增另一套设计语言，不得使用未经确认的核心操作流程。

## 页面布局

### 桌面端（宽度 >= 1024px）

- 左侧为固定宽度导航。
- 右侧顶部展示页面标题和“新建任务”按钮。
- 标题区域下方依次为筛选栏和任务列表。

### 移动端（宽度 < 768px）

- 主导航收起。
- 内容采用单列布局。
- 筛选项空间不足时允许横向滚动或收进筛选面板。
- 页面不得出现非预期横向滚动。

## 内容与组件

- 每条任务展示：标题、状态、负责人和截止日期。
- 默认按最近更新时间倒序排列。
- 长标题最多显示两行，超出部分截断；完整标题可在详情页查看。
- 按钮、输入框、弹窗和提示信息优先复用现有组件。
- 示例数据应覆盖短文本、长文本、空字段和多个状态。

## 页面状态

- 加载中：列表区域显示加载状态，整体布局不得明显跳动。
- 正常数据：展示任务列表和可用操作。
- 空数据：显示“暂无任务”和用户有权限执行的下一步入口。
- 请求失败：显示错误信息及重试按钮。
- 无权限：隐藏无权执行的入口，并阻止通过直接地址或接口操作。
- 部分数据缺失：使用约定的占位方式，不得导致布局错乱。

## 交互规则

- 点击任务进入任务详情。
- 点击“新建任务”打开创建表单。
- 创建成功后关闭表单，并在列表中显示新任务。
- 创建失败时保留用户已经填写的内容。
- 筛选条件变化后更新列表；从详情返回时保留筛选条件和合理的滚动位置。
- 提交期间按钮显示处理中状态并阻止重复提交。

## 可访问性

- 所有核心操作可通过键盘完成。
- 当前焦点具有可见样式。
- 表单控件具有明确标签，错误提示与对应字段关联。
- 图标按钮具有可识别的名称或辅助说明。
- 颜色不能成为表达状态的唯一方式。

## UI 验收

- 分别在 1440px、1024px、768px 和 390px 宽度下检查。
- 页面无元素重叠、文字溢出、控件被裁切或非预期横向滚动。
- 验证加载、正常、空数据、失败和无权限状态。
- 验证鼠标、键盘和触摸设备的核心操作。
- 对关键页面和关键状态保存截图作为证据。
```

## 5. 项目级文档

除了功能和页面规格，还应提供以下项目级文档。

### 5.1 产品总纲

说明：

- 产品解决什么问题；
- 目标用户是谁；
- 用户最核心的使用场景；
- 第一版必须具备哪些能力；
- 哪些需求明确不做；
- 衡量产品成功的指标；
- 功能优先级和发布边界。

### 5.2 术语表

统一业务词汇，避免相同概念在不同文档中使用不同名称。每个术语应包含定义、与相似概念的区别以及必要示例。

### 5.3 业务、数据和状态规则

记录：

- 核心业务对象及字段；
- 对象之间的关系；
- 必填、唯一性和格式约束；
- 状态及允许的状态转换；
- 删除、归档和恢复策略；
- 重复提交和并发修改规则；
- 数据保留和审计要求。

状态较复杂时，应提供状态转换表：

| 当前状态 | 操作 | 下一状态 | 允许角色 | 失败条件 |
| --- | --- | --- | --- | --- |
| 草稿 | 提交 | 待审核 | 创建人 | 必填字段不完整 |
| 待审核 | 通过 | 已发布 | 审核员 | 内容已被撤回 |
| 待审核 | 驳回 | 已驳回 | 审核员 | 无审核权限 |

### 5.4 角色与权限矩阵

| 资源或操作 | 管理员 | 编辑者 | 只读成员 | 未登录用户 |
| --- | --- | --- | --- | --- |
| 查看项目 | 允许 | 允许 | 允许 | 拒绝 |
| 创建任务 | 允许 | 允许 | 拒绝 | 拒绝 |
| 删除项目 | 允许 | 拒绝 | 拒绝 | 拒绝 |

权限必须同时约束界面和服务端，不能只隐藏按钮。

### 5.5 全局设计系统

说明全局 UI 规则：

- 字体、字号和信息层级；
- 颜色及其语义；
- 间距、栅格和断点；
- 按钮、输入框、表格、弹窗等组件用法；
- 加载、空数据、错误和成功反馈；
- 图标来源；
- 响应式和无障碍标准。

若项目已有组件库，应明确要求优先复用，并说明如何查看组件示例。

### 5.6 技术约束和项目约定

至少包含：

- 指定技术栈和版本；
- 项目目录结构和模块边界；
- API、数据库和第三方服务约定；
- 环境变量名称及用途，但不得在文档中记录密钥；
- 安装、启动、构建、测试和代码检查命令；
- 日志、错误处理和监控要求；
- 浏览器、操作系统或设备兼容范围；
- 禁止替换的依赖和需要优先复用的基础设施。

已有代码库时，这份文档必须与真实代码保持一致。

### 5.7 非功能要求

将“性能好”“安全可靠”等要求转成可验证指标，例如：

- 关键页面在约定测试环境下的加载时间上限；
- 列表支持的目标数据规模；
- 敏感操作需要进行服务端权限校验；
- 密钥不得出现在前端代码、日志或版本库中；
- 错误日志包含请求标识，但不得记录密码和令牌；
- 备份频率、恢复目标和数据保留周期；
- 核心服务不可用时的降级行为。

### 5.8 跨功能端到端流程

描述多个功能共同组成的真实用户旅程，例如：

1. 用户注册并完成登录；
2. 创建第一个项目；
3. 邀请项目成员；
4. 创建任务并分配负责人；
5. 负责人完成任务；
6. 创建者归档项目。

端到端流程用于发现单个功能均能使用，但功能之间无法正确衔接的问题。

### 5.9 实施路线图

将项目拆成可独立实现、独立验收的小任务，记录：

- 任务编号和优先级；
- 依赖关系；
- 对应的功能和页面规格；
- 完成状态；
- 风险和待决策事项。

优先完成一条完整的核心流程，再扩展次要功能。

## 6. 统一完成标准（Definition of Done）

一项任务只有满足所有适用条件才算完成：

- 实现内容符合功能和 UI 规格；
- 正常、异常、空数据和无权限路径均已处理；
- 数据和权限检查不仅存在于界面，也存在于服务端；
- 自动化测试通过，并覆盖关键业务规则；
- 代码格式、静态检查、构建和相关回归测试通过；
- 桌面端和移动端不存在明显布局问题；
- 无严重控制台错误、未处理异常或敏感信息泄露；
- 文档与实际实现保持一致；
- 验收证据已提供；
- 已知限制和遗留问题已明确记录。

## 7. Agent 工作规则

建议在仓库根目录使用 `AGENTS.md` 作为所有 Agent 的工作入口，但不要在其中重复全部需求。它应包含：

```markdown
# Agent 工作规则

## 开始任务前

1. 阅读产品总纲、相关功能规格、页面规格和全局约束。
2. 检查现有代码和测试，文档与代码冲突时记录冲突。
3. 确认本次任务范围、依赖和验收条件。

## 实施要求

- 优先复用现有组件、API 和项目模式。
- 不得擅自扩展产品范围或创造关键业务规则。
- 遇到会改变业务结果的歧义时，停止相关决策并提出问题。
- 非关键实现细节可按现有代码约定做合理判断。
- 每次只实现一个可独立验收的任务。

## 验证要求

- 运行项目指定的格式、静态检查、测试和构建命令。
- 根据验收用例验证正常、异常和边界路径。
- UI 任务需检查指定视口和全部页面状态。

## 交付报告

- 已完成的需求；
- 修改的主要文件；
- 执行的检查及结果；
- 验收证据；
- 未解决问题、风险和与规格的偏差。
```

## 8. 编码 Agent 与验收 Agent 的分工

### 编码 Agent

输入：产品文档、相关功能规格、UI 规格、技术约束和完成标准。

输出：

- 代码和必要的数据迁移；
- 自动化测试；
- 本地验证结果；
- 实现说明；
- 已知限制和待决策问题。

编码 Agent 不应以“界面看起来正常”代替验收，也不应自行修改验收标准来适配实现结果。

### 验收 Agent

验收 Agent 应独立依据规格工作，不以编码 Agent 的实现说明作为最终标准。每条验收项输出：

- `通过`：实际结果符合规格，并附证据；
- `失败`：说明预期结果、实际结果、复现步骤和证据；
- `无法判定`：指出缺少的规则或环境条件；
- `阻塞`：指出无法继续验收的外部原因。

建议验收报告格式：

```markdown
## 验收结果：TASK-001

- 结论：失败
- 环境：本地测试环境，Chrome，1440x900
- 用例：AC-03 重复提交
- 预期：只创建一条任务
- 实际：创建了两条相同任务
- 复现步骤：打开创建表单，填写标题，快速双击提交
- 证据：截图、测试日志或相关请求记录
- 严重程度：阻塞发布
```

## 10. 推荐实施流程

1. 先完成产品总纲、核心数据模型、权限矩阵和全局设计规则。
2. 按 `docs/repository-initialization.md` 建立 `AGENTS.md` 和最小工程基线。
3. 按 `docs/development-workflow.md` 建立任务、分支、评审和验收流程。
4. 选择最重要的一条用户旅程。
5. 为这条旅程涉及的功能和页面编写规格及验收用例。
6. 让编码 Agent 一次实现一个可独立验收的任务，并保存会话交接信息。
7. 让验收 Agent 独立执行验收，并提交证据。
8. 将暴露出的歧义补回规格，而不是只在对话中解释。
9. 所有目标 P0 完成后，按 `docs/release-readiness.md` 做发布前检查。
10. 核心流程稳定后，再按优先级扩展其他功能。

不建议在项目开始前穷尽所有细节。先跑通一条从数据、业务逻辑到 UI 和自动化验收的完整路径，再根据实际缺口逐步完善文档，通常更可靠。

## 11. 提交给编码 Agent 的任务模板

```markdown
请实现任务 `TASK-001`。

开始前请阅读：
- `docs/product.md`
- `docs/domain.md`
- `docs/permissions.md`
- `docs/design-system.md`
- `docs/features/TASK-001-create-task.md`
- `docs/pages/task-list.md`
- `docs/definition-of-done.md`

要求：
- 严格限制在本任务范围内；
- 复用现有组件和项目模式；
```
