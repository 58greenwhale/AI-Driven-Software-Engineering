# ADR-0001：MVP 使用固定的三状态任务模型

- 状态：已接受
- 日期：2026-09-18
- 决策人：产品负责人、技术负责人
- 影响范围：任务数据模型、任务列表、筛选和状态更新

## 背景

用户需要区分尚未开始、正在进行和已经完成的任务。候选方案包括简单完成标记、固定三状态模型，以及允许项目自定义工作流。

自定义工作流更灵活，但需要增加状态管理页面、排序规则、迁移规则、权限控制和更多测试。它超出 MVP 验证轻量任务协作的必要范围。

## 决定

MVP 使用三个固定状态：

- `todo`：待处理；
- `in_progress`：进行中；
- `done`：已完成。

新任务始终从 `todo` 开始。允许的转换由 `docs/domain.md` 定义。已完成任务重新打开时进入 `todo`，不直接进入 `in_progress`。

用户不能创建、重命名、排序或删除状态。

## 备选方案

### 方案 A：仅使用“完成/未完成”

优点是模型和界面最简单。缺点是无法区分尚未开始和正在进行，不满足团队了解当前进度的基本需求。

### 方案 B：每个项目自定义状态

优点是适应不同团队流程。缺点是显著增加产品和技术复杂度，也会让跨项目筛选难以保持一致。

### 方案 C：固定三状态模型

能够表达基本进度，同时保持数据、交互和验收简单，因此被采用。

## 后果

正面影响：

- 新项目无需配置即可使用；
- UI、API 和筛选可以采用固定枚举；
- 权限、迁移和自动化测试范围可控。

限制：

- 无法表达“审核中”“已阻塞”等团队自定义阶段；
- 部分用户可能需要通过任务标题或外部工具表达额外状态。

## 重新评估条件

出现以下任一情况时，可以为后续版本重新评估：

- 超过 30% 的活跃项目明确请求自定义状态；
- 固定状态导致核心流程流失或大量外部补充操作；
- 产品引入看板或跨项目工作流功能。

重新评估必须新增 ADR，不直接修改本记录的历史决定。
