# Agent 会话与上下文管理

## 1. 目的

让任务可以跨会话、跨 Agent 恢复，不依赖某次聊天的隐含记忆。聊天内容不是业务事实来源；确认后的规则必须回写规格、ADR 或路线图。

## 2. 任务启动上下文

提交给编码或验收 Agent 的上下文至少包含：

- 任务编号、目标、范围和非目标；
- 必须阅读的产品、领域、权限、架构、功能和页面文档；
- 依赖任务、当前路线图状态和已接受 ADR；
- 验收用例、测试数据、目标视口和完成标准；
- 当前分支、工作区状态、已知风险和外部环境限制。

上下文应引用仓库文件和具体章节，避免复制可能过期的大段需求。

## 3. 会话记录与交接

长任务在阶段结束或切换 Agent 时，保存一份简短交接记录。推荐格式：

```markdown
# TASK-001 会话交接

## 状态
- 路线图状态：进行中
- 当前阶段：服务端校验

## 已完成
- ...

## 修改文件
- `path/to/file`：...

## 验证结果
- `command`：通过/失败/无法执行，原因...

## 已确认假设与决策
- 规则及其来源：...

## 未完成、风险与阻塞
- ...

## 下一步
- ...
```

交接记录应存放在任务交付材料或 PR 中；不要把临时思路伪装成永久规格。

## 4. 上下文边界与恢复

- Agent 发现上下文不足时，先读取引用文档和现有代码，再报告仍缺少的事实；
- 对话中的新业务决定必须同步到规格或 ADR，并说明影响范围；
- 工具失败时记录命令、错误、环境和是否有替代检查；
- 不要通过猜测补齐关键权限、数据、计费、安全或验收规则；
- 新 Agent 接手时以仓库文件、交接记录和测试结果为准，不以口头摘要为准。

## 5. 多 Agent 协作

多 Agent 并行时，任务必须按清晰的文件或职责边界拆分，并指定一个协调者负责合并结果。共享规格、迁移、配置和锁文件由协调者修改；发现边界重叠时先停止冲突部分并重新划分。

验收 Agent 与编码 Agent 保持独立，不共享会导致验收标准被实现影响的未公开假设。验收所需的测试账户、数据和环境应在任务规格中预先定义。

## 6. 证据与敏感信息

保存与结论直接相关的测试日志、截图、请求结果、数据库结果和性能原始数据。证据应标明命令、环境、时间和对应验收用例，但不得包含密码、会话 Cookie、令牌、完整认证头或真实个人数据。
