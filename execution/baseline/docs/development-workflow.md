# AI 开发工作流

## 1. 范围

本流程覆盖需求已经确认后的开发阶段：任务就绪、Agent 实现、自动化验证、代码评审、独立验收和合并。产品发现、实际部署、日常运维和产品运营不在本流程内。

## 2. 任务状态与进入条件

路线图任务按以下状态流转：

```text
待决策 -> 就绪 -> 进行中 -> 待验收 -> 完成
                         └-> 阻塞
```

任务只有在以下条件满足后才能进入“就绪”：

- 功能范围、非目标、依赖和权限规则已确认；
- 相关功能/页面规格和验收用例已存在；
- 关键技术决策已有 ADR，或明确标记为不阻塞；
- 测试数据、验证命令和完成标准可执行；
- 没有会改变业务结果的未决问题。

## 3. 可追踪性

每个任务应保持以下关联：

```text
路线图任务 -> 功能/页面规格 -> 验收用例 -> 测试 -> PR -> 验收报告 -> 交付报告
```

任务编号应出现在分支、PR 标题或描述、测试说明和交付报告中。发现规格变化时，同步更新受影响的引用、验收用例、依赖和路线图状态。

## 4. 编码与交接

编码 Agent 开始前读取任务要求的文档，确认工作区和依赖状态，并在报告中记录实现假设。实现期间只处理当前任务，不以新增功能掩盖测试失败或规格歧义。

编码完成后必须：

1. 运行实际存在的格式、静态检查、测试和构建命令；
2. 验证验收用例涉及的正常、异常、边界和权限路径；
3. 更新路线图为“待验收”；
4. 提供改动文件、检查结果、证据、风险和未决事项；
5. 将可复现的上下文交给独立验收 Agent。

验收 Agent 不修改产品实现。验收失败时回到“进行中”，只修复失败原因；不得修改验收标准迁就实现。

## 5. 分支、提交与评审

- 每个任务使用短生命周期分支，例如 `task/TASK-001-create-task`；
- 提交使用简洁的祈使句，可带范围，例如 `feat(tasks): create task form`；
- PR 必须包含任务编号、范围摘要、规格链接、测试结果、证据、风险和未解决事项；
- 评审至少检查规格符合性、权限和数据安全、错误路径、测试覆盖、模块边界和无关改动；
- 合并前必须通过 CI 检查、必要的代码评审和独立验收；
- 受保护主分支不允许绕过检查强制推送。

## 6. 变更、失败与阻塞

- 需求变化：先更新规格和路线图，再修改实现；影响多个功能或难以回退时新增 ADR；
- 测试失败：记录失败命令和原因，修复后重新验证，不得删除或放宽测试；
- 规格冲突或关键规则缺失：暂停受影响工作，记录冲突、影响和需要的决策；
- 外部环境不可用：标记“阻塞”，提供复现信息和不依赖该环境的替代检查；
- 技术债务和已知限制：写入交付报告，并创建后续任务，不隐藏在实现细节中。

## 7. 任务完成门禁

任务只有同时满足以下条件才能标记“完成”：编码自检通过、自动化测试通过、独立验收结论为“通过”、PR 已合并、相关文档与实际行为一致。发布级检查由 `docs/release-readiness.md` 单独负责。
